Summary

  • Fastest safe step: adopt Forge with the same app key and keep the Connect modules for now. Customers keep their installs, licences and data, and you can ship updates again.
  • What Atlassian counts as done: an app with a Forge manifest is still a Connect app until every Connect module is gone. The plan in section 5 gets you to zero.
  • High-risk items: jiraIssueFields.

2Custom fields: keeping existing values

The app defines three issue fields: one that users edit (Size) and two that the app computes (Detected Size, Detected Quality). They are the main risk, because saved filters, boards and dashboards on customer sites refer to them.

FieldTodayForge targetWhat to watch
SizeEditable Connect fieldjira:customFieldThe field id changes, so saved filters and board quick filters that use it stop matching.
Detected SizeRead-only, set by the appjira:customField, read-onlyValues must be back-filled for existing issues.
Detected QualityRead-only, set by the appjira:customField, read-onlySame as Detected Size.

Recommended sequence

  1. Step 1 keeps all three as Connect modules, so nothing changes for customers.
  2. Add the Forge fields next to the old ones and write to both for one release.
  3. Back-fill existing values with a background job: Forge async events, in batches, with a resume marker.
  4. Ship a short admin guide: which filters to edit, with a JQL find-and-replace example.
  5. Hide the old fields, then remove them in the next release.

3Scopes and consent

Connect scopes today: READ, WRITE.

  • Forge uses granular scopes. Asking for more than before triggers an admin approval on upgrade, so list only what the app calls.

Likely Forge scopes: judging from the modules alone, read:jira-work and write:jira-work, plus storage:app if tenant settings move into Forge storage. Confirm the list against the REST endpoints the backend calls before publishing.

4Webhooks to Forge triggers

Connect webhookForge trigger event
jira:issue_updatedavi:jira:updated:issue
jira:issue_deletedavi:jira:deleted:issue

Forge event payloads have a different shape from Connect webhook bodies, so handlers need adapting. Check that every field your handler reads is still in the payload, or fetch it with one REST call.

5Migration plan

Week 12–3 days

Adopt Forge

Declare the migration plan in the Partner Portal. Generate the manifest with Atlassian's @atlassian/connect-to-forge, compare it with the draft in the appendix, register the app with the same key and test the upgrade on a copy of a real site. Make sure the uninstalled callback that adopters see during the upgrade cannot delete tenant data.

Weeks 2–43–5 days

Direct replacements

Global page, project page, issue panel and the two entity properties move to jira:globalPage, jira:projectPage, jira:issuePanel and jira:entityProperty.

Weeks 4–52–4 days

Rework

The story dialog becomes a Forge modal, the web panel moves to its issue-view location and both webhooks become Forge triggers.

Weeks 6–83–7 days

Custom fields

New Forge fields, back-fill and the admin guide, as in section 2. This release removes the last Connect module.

Total10–19 developer days

Before each step, send customers a short notice that explains any new consent screen.
